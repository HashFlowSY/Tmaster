# 生辰引导用可跳过的软提示,而非登录硬门

登录/注册后,若命主尚未建立 BirthProfile,做一次**可跳过的软引导**——把用户带到 onboarding,而不是设一道「没生辰就禁止进入任何页面」的硬登录门。登录时查 `BirthApi.get()`:404(无生辰)或网络失败**都引导**(fail-toward-引导——因为可随时跳过,最坏只是让有生辰的人被多推一次);boot / 恢复会话**不**引导(只在显式 login/register 时推一次);不记忆「已跳过」,每次登录重查。落点:保存成功进 `/chart`,跳过进 `/chat`。

需求最初提的是「没生辰就禁止进入其他页面」的硬门,grilling 过程中改为软引导——理由见下。

## Considered Options

- 硬登录门(无生辰禁止进入任何页面):被否。与 ADR-0004 已确立的「奇门不需生辰」直接冲突,会把只想用奇门的用户 trap 在门内;且 v1 无任何「改生辰」入口,一道硬门等于把不愿填的人永久锁死(只能卸载);实现上还要 RootNav 维持一道三元常驻门禁。
- 完全不引导,只靠点用处补(chart 空态 / 八字对话的 `birth_required` 409):被否。点用引导确已存在(见 Consequences),但登录后主动推一次能明显提高生辰完成率,而成本极低。
- 软引导 + 持久记忆「已跳过」(账号一辈子只推一次):被否。需持久化跳过态,且跨设备 / 重装会重置;而 boot 不引导、6h 滑动会话下重新登录本就不频繁,「每次登录推一次」的打扰已足够低,不值得引入这份状态。

## Consequences

- 无生辰的用户登录后被带到 onboarding,但随时可「稍后填写」离开,不被 trap。
- 网络抖动时,有生辰的老用户可能被多推一次 onboarding,点跳过即走;若其执意重填会 upsert 覆盖原盘——属可接受的边缘,由跳过路径规避。
- 本引导与点用引导并存互补:`chart.tsx` 空态、`chat.tsx` 的 `birth_required` 弹窗在「用时」补;本引导在「登录入口」推。
- 服务端维持既有 `409 birth_required` 作数据完整性兜底,不新增强制层——ADR-0002 局域网、可信用户、v1 命主=本人 的前提下已足够。
- RootNav 仍是单一导航真相源:落点由登录流预先算好的 nudge 标志决定,顺带消除注册页旧有的「`replace` 竞态 / 死返回键」。
- onboarding 从「事实上的必经步骤」正式定性为可跳过引导;v1 仍无独立「改生辰」入口,后续如需再另起页承载。
